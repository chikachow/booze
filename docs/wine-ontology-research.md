# Wine identity and optional wine names

Research date: 22 September 2026. Scope: the capture flow's assumption that every wine needs a separate name, and the smallest sound distinction between label facts, display text and identity. Recommendations below are application design judgments, not requirements imposed by a wine standard.

## Finding

A proprietary wine/cuvée name is **optional**. A useful catalogue title can be assembled from producer or brand, a variety/blend or appellation, any evidenced range/cuvée/site qualifier, and vintage when known. A generated title is presentation, not evidence that the label carries a proprietary name and not a unique identifier.

The strongest counterexample comes from Rikard itself: its catalogue lists **2023 RIKARD Chardonnay** and **2023 RIKARD Black Label Chardonnay** together. Both share producer, grape and vintage. Therefore `producer + grape + vintage` is demonstrably unsafe as a unique key, even for the producer involved in this capture investigation. [Rikard Chardonnay catalogue](https://www.rikardwines.com.au/varieties/chardonnay/).

## Narrow recommendation

1. **Clarify what `name` means before changing storage.** If it means a proprietary/cuvée designation, make it optional. If it means the catalogue's display title, a derived title can satisfy that purpose without pretending a proprietary designation exists. Do not silently overload one field with both meanings.
2. **Capture facts independently.** Keep producer/brand, variety or blend, origin/appellation, optional distinctive designation and vintage separate to the extent the existing model permits. Producer and brand may coincide; they are not guaranteed to. Avoid introducing a full commercial-party ontology just to unblock this capture.
3. **Compose a display label from supported facts.** Illustrative output: `RIKARD Chardonnay 2023`; include `Black Label` when evidenced. Support appellation-led labels as well. Preserve an explicit title when it contains useful information a formatter cannot reconstruct. Do not duplicate producer/year/grape text already present in a full title.
4. **Keep stable record IDs.** Use producer, variety, vintage and qualifiers to find possible matches, not as a uniqueness constraint or unconditional merge instruction. Missing qualifier evidence must not automatically select the standard wine when another range is plausible.
5. **Keep unknown distinct from absent.** A missing extracted vintage means unknown, not necessarily NV. A missing designation can mean none exists, unreadable text, or incomplete capture. Allow the capture to remain reviewable without inventing facts. Record explicit NV when actually supported.
6. **Keep the bottle/capture distinct from the wine record.** Photos and extraction claims belong to their capture evidence; ownership, acquisition, location and consumption concern physical stock. This is a boundary to preserve, not a proposal to rebuild inventory now.

These are design inferences from the distinctions above. No source establishes a universal minimum combination that uniquely identifies every wine.

## Current Booze model and the capture failure

The coordinator inspected the deployed code at `70b33e0dae9947222dccc10abee349b30208e6b3`:

- `packages/db/src/schema.ts` already permits null `wine_vintages.designation`, but requires `base_name` and `display_name`. Its unique key is site, winery, base name and vintage label.
- `apps/web/worker/bottle-extractor.ts` copies the extracted display name into all three fields: `baseName`, `designation` and `displayName`. Its prompt asks for distinctive range, series, block, vineyard or cuvée terms and instructs the model to leave uncertain facts empty.
- `apps/web/worker/routes/bottle-captures.ts` rejects manual creation when the candidate's designation is empty. `apps/web/worker/bottle-importer.ts` similarly treats an empty designation as insufficient for matching.
- `apps/web/worker/api/catalogue.ts` falls back from missing base name/designation to the producer name, then reuses records on winery, base name and vintage. Removing only the capture guard could therefore conflate different unnamed wines from the same producer and year. The fallback ignores grape composition.
- `apps/web/worker/api/ids.ts` maps an absent vintage year to `NV`; this conflates missing evidence with an explicitly non-vintage wine.
- The browser only accepted `application/json` errors, while the API returns `application/problem+json`. A focused regression test reproduced the loss of the useful message, and a separate local fix now preserves the API detail and displays it on the capture card. That change is not yet deployed.

The actual Rikard capture's visible facts include producer RIKARD Wines, vintage 2022 and grape Shiraz, while the name/designation fields are absent from the review. A single user-authorized production retry reproduced the generic failure and retained the capture in review. The raw production HTTP error body was not available through the browser tooling, so the missing-designation explanation is supported by the visible data and reproduced route behavior, rather than a captured production response.

The resulting implementation allows optional proprietary designations, derives a display description such as `2022 RIKARD Shiraz` from supported facts, and revises matching and creation together so a generated description cannot silently merge distinct wines. It preserves capture/run idempotency and original extraction evidence. The accepted behavior and local validation are recorded below; production deployment and import are separate steps.

## Edge cases and limits

- **Same producer, grape and year:** range, named vineyard, appellation, cuvée or another designation can matter; Rikard's Black Label is a concrete collision. Even adding a display name does not make a universal natural key.
- **Cuvée is not a universal synonym for proper name:** OIV also uses it technically for a product destined for secondary fermentation; Comité Champagne uses it for the first pressing juice fraction. Prefer an explicit field meaning such as optional proprietary designation, and retain the label's wording. [OIV sparkling-wine definitions, II.4.1.2](https://www.oiv.int/de/standards/international-code-of-oenological-practices/part-ii-oenological-treatments-and-practices/special-wines%3A-sparkling-wines), [Comité Champagne: from terroir to wine](https://www.champagne.fr/system/files/2022-11/brochure_civc_2020_en_bd.pdf).
- **Blend or appellation-led wine:** a single required grape field is unsuitable. OIV explicitly separates varietal information from product denomination and geography. Do not infer exact blend percentages from a single varietal label. [OIV optional information](https://www.oiv.int/standards/international-standard-for-the-labelling-of-wines/part-iii-optional-information/optional-information).
- **NV, unknown year, release and batch:** NV is an explicit product description; an unreadable year is uncertainty. Different physical bottles or batches may share the same display label. Batch and instance identity are separately represented by GS1. [Rikard catalogue](https://www.rikardwines.com.au/varieties/chardonnay/), [GS1 traceability](https://www.gs1.org/standards/gs1-global-traceability-standard/current-standard).
- **W3C example limitations:** it was built to explain description logic/OWL; `Wine` and `Vintage` reflect modeling choices in that example. The guide itself discusses alternative representations and exactly one year per Vintage. It is not evidence that every product has a vintage, one unambiguous maker, a separate proper name, or a globally unique producer/variety combination. [OWL Guide](https://www.w3.org/TR/owl-guide/).
- **VIVC verification boundary:** direct database retrieval returned 403. Its ownership/purpose and synonym problem were verified from JKI; the concrete Shiraz/Syrah example was verified from UC Davis. No live VIVC record identifiers, current dataset completeness, import/API terms or redistribution rights were verified. A future normalized vocabulary integration needs those checks.
- **Standards scope:** OIV is used here for conceptual distinctions, not a determination of Australian or other local legal compliance. Its March 2024 PDF contains older varietal wording; the [2024 amending resolution](https://www.oiv.int/node/3815) and current HTML differ. This note deliberately does not translate labelling thresholds into application validation rules.
- **Capture boundary:** current producer web pages establish examples and counterexamples, not the identity of the user's photographed bottle. That needs the actual capture evidence. This research did not alter production data.

## Accepted application behavior

The user confirmed these choices after reviewing the evidence:

- Proprietary designation is optional. Producer/brand, grape composition or appellation, and known vintage can provide a useful generated title. The title and descriptive fields are not unique keys.
- “Create new” creates a distinct wine record. Capture retries replay the original import receipt rather than creating another set of bottles. Possible existing wines require explicit selection; confident new captures with no plausible match can still import automatically.
- Unknown vintage and explicit non-vintage are separate states. Historical `NV` values cannot establish non-vintage because the previous implementation used them for missing years too. Known years remain known, including writes made by the old Worker during deployment overlap.
- A user can explicitly save unidentified wine inventory. An absent producer has no winery relationship; it does not create a shared fictional producer.
- Capture review supports manual entry and corrections, including failed extraction. Saving corrections does not import bottles. Corrections persist separately from original extraction evidence and survive extraction retries; a manually corrected capture requires explicit import.
- Shared wine correction and reassigning one bottle are separate actions. Shared correction shows and verifies the affected bottle count. Existing-wine selection does not change that wine's facts. New-wine reviews and awards require fresh entry rather than implicit transfer.
- Catalogue identity changes use a forward migration and preserve existing wine and bottle IDs. No automatic data merging, external vocabulary ingestion, or evidence-based reinterpretation of old captures is part of this change.

Validation includes populated local D1 upgrade/replay, preserved catalogue and extraction records, schema export parity, capture review concurrency and import receipts, shared-edit scope and interleavings, nullable-producer API/MCP reads, and frontend review/edit behavior. These are local checks; they do not establish the state of production or import the Rikard capture.
